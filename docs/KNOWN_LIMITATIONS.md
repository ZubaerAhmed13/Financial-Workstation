# Known Limitations

These limitations are intentionally explicit. They are not silently presented as institutional-grade precision.

1. **Bond settlement conventions:** the current workstation bond workflow is period-based. It does not yet provide full settlement-date clean/dirty pricing, accrued-interest schedules, ex-coupon handling, business-day calendars, or selectable Actual/Actual, 30/360, Actual/360, etc. day-count conventions.
2. **Bond optionality:** option-adjusted spread, callable/putable bond trees, key-rate duration and full term-structure bootstrapping are outside the certified core in this pass.
3. **Residual income:** the compatibility wrapper uses a simplified clean-surplus/retention convention because the existing UI does not expose a full dividend/payout/book-value forecast. Model realism depends on user inputs.
4. **Frequency inference:** some legacy risk views still describe imported price histories as daily and use 252 periods/year. The certified core requires an explicit annualization frequency, but not every legacy screen asks for it.
5. **Recovery unit:** the current price-history UI reports recovery in observations. Calendar-day recovery is available in the certified core when timestamps are supplied, but the legacy card does not render both measures.
6. **Market data:** the workstation remains offline-first and does not provide a live institutional market-data feed. Imported/user-entered data quality directly affects results.
7. **IRR multiple roots:** the certified IRR returns a bracketed root where one is found. Non-conventional cash flows can have multiple economically valid roots; users should inspect sign changes and NPV profiles.
8. **XIRR day basis:** XIRR uses a 365-day year convention in the certified core and production runtime.
9. **VaR / Expected Shortfall:** results remain model- and sample-dependent. Parametric, historical and Monte Carlo methods can disagree materially.
10. **Accounting framework comparability:** IFRS/US-GAAP awareness and accounting-quality tooling do not replace an accounting-policy review of issuer filings.
11. **Specialized accounting scores:** the shared ratio layer is hardened for zero/missing semantics. Specialized scoring frameworks retain their own assumptions unless explicitly routed through a certified core.
12. **JavaScript numeric model:** calculations use IEEE-754 double precision. This is appropriate for analytical modeling but not a decimal-ledger/accounting-posting engine.
13. **Three-statement forecast assumptions:** `FinancialModelCore` now certifies forecast mechanics, debt aggregation, cash-flow coupling, working-capital mechanics, reconciliation behavior and zero preservation. It remains a simplified analytical model: there is no full tax-loss carryforward engine, lease accounting schedule, deferred-tax roll-forward, share-based-compensation roll-forward, acquisition accounting, revolver/minimum-cash financing solver, circular interest calculation, or detailed retained-earnings/dividend module.
14. **Opening balance sheet:** the certified model deliberately does not hide an unbalanced opening balance sheet with a cash plug. If user-entered starting assets do not equal liabilities plus equity, the difference is carried and disclosed. Users must reconcile source inputs if they want a fully balanced forecast.
15. **EBITDA margin semantics:** detailed COGS, SG&A and R&D assumptions determine modeled EBITDA. The separate EBITDA-margin series is explicitly a target/diagnostic. A material mismatch generates a caution rather than silently forcing one set of assumptions to agree with the other.
16. **Debt schedule:** current certified debt modeling supports simultaneous instruments with fixed rates and fixed annual repayment/amortization. It does not yet model floating-rate curves, refinancing, PIK interest, mandatory-vs-optional sweeps, fees, covenant cure rights or instrument-specific maturity dates.
17. **ECL:** certified production ECL validates PD, recovery and EAD and preserves zero exposure, but it remains a point-in-time `PD × LGD × EAD` calculation. IFRS 9/CECL staging, lifetime term structures, macro overlays and contractual cash-flow timing require a more detailed credit-loss engine.
18. **Browser smoke scope:** the expanded CI pass is green across pinned Chromium, Firefox and WebKit desktop engines, plus a Chromium 390×844 responsive viewport. Each pass opens all 42 discovered views and activates all 59 tabs with no page/console errors or external HTTP(S) requests and executes 11 production runtime calculations. This is broad application smoke coverage, not exhaustive every-input workflow proof.
19. **Mobile coverage:** the 390×844 Chromium pass verifies responsive overflow and the menu/sidebar interaction in headless automation. It is not equivalent to certification on physical Android/iOS devices, touch keyboards, orientation changes, OS accessibility settings or every mobile browser build.
20. **Legacy monolith scope:** every current static-audit regex lead in the deployable monolith is inventoried and context-classified, but broad regex matches are not equivalent to defects. Certification applies strictly to `FinanceCore`, `FinancialModelCore`, and production paths explicitly mapped/tested through them, plus the explicitly hardened XIRR/ECL paths. Other legacy analytical helpers remain outside the certified boundary until separately tested and promoted.
21. **Static-audit count:** the expanded deployable artifact currently contains 425 broad pattern leads, 220 conservatively categorized as calculation-sensitive or algorithmic-review, with 0 unclassified. These counts are an audit inventory, not a claim of 220 remaining bugs.
